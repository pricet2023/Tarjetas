# Tarjetas — Spanish flash cards

A local-first flash card app for learning Spanish. Two-sided cards (English /
Español), a shuffled study deck you swipe through, and translation suggestions
while you type a new card.

Runs entirely against the **local Supabase stack** — there is no remote project
and no CI/CD wiring yet.

## Stack

| Layer      | Choice                                                  |
| ---------- | ------------------------------------------------------- |
| Front end  | Vite + React 18 + TypeScript + Tailwind                 |
| Data       | Supabase Postgres — shared deck, per-user progress       |
| Auth       | Supabase Auth (email + password)                         |
| Server     | Supabase Edge Functions (Deno) — `translate`             |
| Translation| MyMemory free API, behind a swappable provider interface |

## Getting started

Docker Desktop must be running.

```bash
npm install
npm run db:start          # boots Postgres, Auth, Studio, Edge Runtime
cp .env.example .env      # then paste the anon key from the db:start output
npm run db:types          # generate src/types/database.types.ts
npm run dev               # Vite on :3000 + edge functions on :54321
```

Open http://localhost:3000, create an account (email confirmation is disabled
locally, so you're signed straight in), and add a card. Every account on the
instance shares one deck of cards and keeps its own progress through it, so a
second person signs up the same way and starts from zero on the cards already
there.

Useful local URLs:

- App — http://localhost:3000
- Supabase Studio — http://127.0.0.1:54323
- Mailpit (auth emails) — http://127.0.0.1:54324

## Schema

`supabase/migrations/`, applied in numeric order:

- **001_cards** — `public.cards`: `english`, `spanish`, optional `notes`.
  Originally per-user, with denormalised review counters and unique on
  `(user_id, english)`; both of those change in 009.
- **002_reviews** — `public.card_reviews`: append-only log, one row per swipe,
  recording `knew` and which side was the prompt. A trigger rolls each review
  up into the reviewer's scheduling state.
- **003_rls** — the original "every row is private to its owner" policies,
  replaced for `cards` in 009. Reviews are insert-and-read only.
- **004_study_deck** — the original uniform shuffle, superseded by 008.
- **005_word_frequency** — 29,854 Spanish words with Zipf frequencies, plus
  `phrase_zipf()`. Generated by `scripts/gen-word-frequency.py`; reference data,
  readable by any signed-in user.
- **006_review_timing** — `card_reviews.response_ms`.
- **007_card_state** — per-`(card, direction)` scheduling state: `streak`,
  `lapses`, `reps`, `last_reviewed_at`, maintained by the review trigger.
- **009_shared_deck** — one deck, two learners. `cards` becomes shared
  (`user_id` -> `created_by`, unique on `english` alone, any signed-in user can
  add, edit or delete any card) while progress stays private: `card_state` is
  keyed on `(user_id, card_id, prompt_side)` and the review counters move off
  the card into `card_state`, read back per user through the `card_progress`
  and `cards_with_progress` views.
- **010_study_deck** — the same weighting as 008, joined to the caller's own
  `card_state`. See below.
- **011_seed_cards** — the starter deck: 3,479 cards. 100 verbs x (5 simple
  tenses x 6 persons + the infinitive), plus 379 common words and phrases.
  Generated by `scripts/gen-seed-cards.py`; see "The starter deck" below.
- **012_phrase_zipf_probe** — `phrase_zipf` as an index probe rather than a
  join. The 005 version hash-joined the 30,000-row frequency table on every
  call, which cost 2ms a card: fine for a hand-made deck, 14 seconds once 011
  seeded 3,479 of them.
- **013_pronunciation** — `'pronounce'` becomes a third `prompt_side`;
  `card_reviews` gains a nullable `score` and `phone_scores`; `phone_state`
  accumulates per-user, per-phoneme skill. Progress, so RLS'd to the caller.
- **014_phone_scheduling** — `phrase_phones` (the phonemes of a card face,
  shared reference data) and `phone_ability()` (a Thompson draw per phoneme),
  plus the `study_deck` revision that spends them. See "Pronunciation" below.
- **015_seed_phrase_phones** — the seed deck through the app's own G2P: 3,407
  card faces. Generated by `npm run db:phones`.

## The starter deck

`011_seed_cards.sql` ships 3,479 cards, generated by `scripts/gen-seed-cards.py`
(`.venv/bin/pip install wordfreq verbecc` first). They have `created_by = null`:
they belong to the deck rather than to either of us.

**3,100 conjugation drills** — the 100 most common verbs across the present,
preterite, imperfect, simple future and conditional, in all six persons, plus
each infinitive:

| Prompt | Answer |
| --- | --- |
| `I spoke (hablar, preterite)` | `yo hablé` |
| `he/she used to speak (hablar, imperfect)` | `él hablaba` |
| `they will be able to (poder)` | `ellos podrán` |
| `to be able to (can)` | `poder` |

The verb list is ranked by corpus frequency over each verb's imperfect,
preterite, future and conditional forms — scoring the present too puts `parar`
second, because "para" is a preposition — and then curated; the script
documents every deviation. The Spanish is looked up in `verbecc`'s conjugation
tables rather than derived from endings, and the generator asserts 99
hand-verified forms (`anduve`, `hizo`, `querré`, `empecé`, `oyó`, `conozco`, …)
before it will write the file. `verbecc` puts the impersonal `hay` in *haber*'s
third-person present slot, where the paradigm form is `ha`; that one is
overridden.

The prompt carries the infinitive on purpose — the skill being drilled is the
conjugation, not the vocabulary — and the answer keeps its subject pronoun,
because the imperfect and conditional have identical `yo` and `él` forms and the
Spanish→English direction would otherwise be a coin toss. "you (plural)" is
`vosotros`; every such card notes that Latin America uses `ustedes` with the
`ellos` form.

`gustar` and `nacer` are deliberately *not* drilled: "yo gusto" doesn't mean "I
like", so gustar appears as the `me/te/le gusta` phrases instead.

**379 words and phrases** — numbers, days, months, family, food, house, body,
colours, adjectives, adverbs, places, transport, weather, and the greetings and
survival phrases. Nouns carry their article (`la casa`, not `casa`) so the
gender is learned with the word, with notes where Spain and Latin America
differ (`el coche` / `el carro`, `la patata` / `la papa`) or where the gender is
a trap (`el agua` is feminine, `la mano` isn't masculine).

On a brand-new account the first sessions are five cards long: `new_limit`
caps unseen material at 5 per deck, and at first everything is unseen. It fills
out as cards come back for review — raise `newLimit` in `src/pages/Study.tsx`
if that's too slow a start.

## Studying

`/study` deals a deck from the `study_deck` SQL function. Tap a card (or press
Space) to reveal the other side; swipe right for "knew it", left for "didn't" —
arrow keys do the same on a desktop. Every swipe writes a `card_reviews` row
including how long the card was on screen.

### The scheduling algorithm

Cards are drawn by **weighted random sampling**, not ranked — a plain ordering
would show the same few cards every session. Since migration 016 the weight is
one term:

```
weight = urgency
```

**urgency — how likely you are to have forgotten it.**

```
halflife = 1h x 3^min(streak, 7) / (1 + 0.35 x lapses)
urgency  = 1 - exp(-elapsed / halflife)
```

`streak` is consecutive correct answers *by you*, reset by any wrong one. It is
used in preference to the lifetime `times_known/times_seen` ratio, which can't
tell 1/1 from 20/20 and still calls a card you've just forgotten 95% known.
`lapses` counts right-then-wrong transitions, so a card that is *personally*
difficult keeps a shorter interval even after a fresh streak.

The resulting ladder of review intervals:

| streak | 1 | 2 | 3 | 4 | 5 | 6 | 7+ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| halflife | 1h | 3h | 9h | 27h | 3.4d | 10d | 91d |

**Relearning.** A card whose streak is 0 despite having been reviewed is one
you got wrong and haven't since fixed. The forgetting curve is the wrong model
for it — it says "you saw this a minute ago, so you remember it" when you
demonstrably don't — so those are held at an urgency floor of 0.6 until
answered correctly, on a ten-minute halflife rather than the one-hour base.
That keeps a failed card at the top of the next deck rather than behind the
new material.

**Cooldowns.** Independent of any weighting, and applied first:

- a card is not dealt twice within **one hour**;
- a card is not dealt more than twice within **six hours**.

Per card, not per direction — being asked "ya" in either direction is still
being asked "ya".

**Two lanes.** Half the deck is reserved for cards you have never seen
(`new_limit`, default 10 of 20) and half for review, each filled by its own
race. The reservation matters: as a plain eligibility cap the new cards simply
lost every slot to overdue ones, and ten consecutive decks came back with one
new card each. Whichever lane runs short the other tops the deck up, so a first
session is a full 20 new cards and a deck is never returned short.

**Other behaviour**

- **Shared deck, separate decks.** Every card is drawn from the one shared
  portfolio, but weighted by the signed-in user's own reviews — the same cards
  deal two different sessions to two people, and neither can retire a card out
  of the other's rotation. The counters on the card list are yours alone.
- **Direction.** Scheduling is per `(card, direction)`. Recognising "la casa"
  arrives long before producing it, so the two are tracked separately and a
  deck picks whichever direction of a card is weaker. One direction per card
  per deck.
- **No in-session retry.** A card is asked once per session and the queue only
  shrinks (`src/app/lib/session-queue.ts`). The retry is the scheduler's job,
  an hour later at the earliest. It used to be requeued four places back,
  indefinitely, which meant a card you couldn't get right came round every
  fifth card for the whole session.
- **What was dropped.** The weight used to be `urgency x utility`, where
  utility was corpus word frequency on the Zipf scale. The two terms were not
  comparable: urgency saturates near 1.0 for anything not just-answered, while
  utility spanned 6.7x, so the deck was in effect ranked by how common — which
  is to say how easy — the Spanish word was. `phrase_zipf` is still there and
  still an index probe; the scheduler just doesn't consult it.

### Tuning it

Everything above lives in `supabase/migrations/016_deck_variety.sql`, so
changing the algorithm is a migration and no app deploy. The two knobs worth
reaching for first are the halflife base (reviews too dense or too sparse) and
`newLimitFor` in `src/pages/Study.tsx` (how fast you work through the deck).
`study_deck` returns each row's `weight` and `is_new` alongside the card, which
is what the "New" chip on the study screen reads.

`response_ms` is recorded on every review but not yet used. It's the obvious
next input — answering correctly after five seconds is much weaker than
answering instantly.

## Pronunciation

A third direction. The card shows the English, you hold the mic and say the
Spanish, and you get told **which sound was wrong and what it came out as** —
"that was a tap, not a trill" rather than "72%".

Everything runs on the device. The model is downloaded once (197 MB, cached by
the Cache API), inference happens in a Web Worker, and no audio leaves the
machine. There is no API and no per-use cost.

### Why not just transcribe it

A speech-to-text model would be the obvious thing and it cannot do this job.
It carries a language-model prior — it *knows* *casa* is a likely Spanish word
and will emit it from mangled audio, because it is built to be forgiving and we
need it to be picky. It also can't localise ("wrong" doesn't say which sound),
can't give a degree (borderline and catastrophic look identical), and normalises
away exactly the distinctions being scored.

So the pipeline scores against a *known* target instead:

```
spanish  ──g2p──▶  /k a s a/  ──buildTarget──┐
                                             ├─▶ forcedAlign ─▶ spans ─▶ GOP ─▶ per-phone verdict
microphone ──▶ 16 kHz mono ──▶ wav2vec2 ──▶ logProbs ─────────┘
```

### The four pieces

**G2P** (`src/app/lib/phonology/`) — spelling to phonemes, ~400 lines of rules
and no dictionary, because Spanish orthography is shallow enough for that to
work. Latin American: seseo (`cielo` → /s/) and yeísmo (`llave` → /ʝ/). It
syllabifies and assigns stress too, since a stressed vowel is longer and
clearer and misplacing it is audible. Allophones are deliberately *not*
distinguished — Spanish /b/ is [b] after a pause and [β] between vowels and no
native hears a difference, so scoring them apart would penalise correct
Spanish. /ɾ/ and /r/ *are* kept apart: that contrast is the feature.

**The acoustic model** (`src/app/lib/acoustic/`) —
`wav2vec2-xlsr-53-espeak-cv-ft`, q4f16 ONNX, 197 MB, emitting a distribution
over 392 IPA labels every 20 ms. `inventory.ts` is the only place our 24 scored
units and its 392 labels are related, so swapping the model is a one-table
change.

**Forced alignment** (`src/app/lib/align/ctc.ts`) — Viterbi over the CTC state
lattice: given that the target was /k a s a/, *when* was each part said? The
answer is what makes the feedback per-phoneme instead of per-word, and it is
what solves credit assignment for the learner model below.

**GOP** (`src/app/lib/phonology/gop.ts`) — Goodness of Pronunciation, a
comparison rather than a probability:

```
GOP(p) = log P(p | frames) - max log P(q | frames)
                             q != p
```

*How much better does the intended sound explain this audio than the best rival
does?* `P(/r/) = 0.4` means nothing alone; it is excellent if every rival scored
under 0.1 and wrong if tapped /ɾ/ scored 0.55. And because we know **which**
sound won instead, the feedback can name it.

### The three things that are easy to get wrong

- **The blank must be excluded from the rival set.** CTC models are peaky: on a
  *native* recording of *perro*, `<pad>` is the argmax on 24 of 30 frames. Left
  in, GOP measures how blank a frame is rather than how well it was pronounced.
- **GOP is not comparable across phonemes or speakers.** /a/ is distinctive and
  always scores well; /r/, /ɾ/ and /l/ crowd each other even for natives. So a
  single global threshold nags about /r/ forever and never catches /x/. Scores
  are reported as a **z-score against native speech**, measured per phoneme on
  FLEURS es_419 by `npm run stats:native` — and with the *same quantized build*
  the app runs, or the quantization bias doesn't cancel. The committed baseline
  is 165 clips and 20,004 phone spans, and it makes the point on its own: a
  native's /l/ beats its best rival by 6.4 nats and a native's /r/ by 0.4.
- **There are no labels.** Nobody is marking attempts right or wrong, so this is
  anomaly detection against a reference distribution, not classification. The
  flag line is the 5th percentile of native speech for that phoneme — "flag what
  fewer than one native in twenty would produce" — which is a *design choice*,
  stated as one in the code, not a measurement.

Durations are deliberately not used. Alignment yields them for free in
principle, but this model is peaky enough that Viterbi gives every phoneme
exactly one frame, so a span is a peak locator and not the edge of a sound.

### Feeding it back into the scheduler

This is the part that changes the deck. The existing scheduler models knowledge
per `(card, direction)`, so an unseen card has nothing to go on — hence the flat
`0.85` unseen urgency, a constant precisely because a card has no history. **A
phoneme has one**, and phonemes are shared across the whole deck, so a card
containing /r/ and /x/ is predictably hard before it has ever been attempted.

- `phone_state` (013) accumulates hits, near misses and misses per phoneme per
  user. Alignment is what makes this identifiable: when an attempt goes badly it
  says *which* sound was at fault.
- `phrase_phones` (014/015) holds the phonemes of each card face, because the
  weighting lives in SQL and G2P is TypeScript. Keyed on the Spanish text, so
  it's the same reference-data-plus-index-probe shape as `word_frequency`.
- `phone_ability()` draws one **Thompson sample** per phoneme per deck build
  from a Beta posterior. A sound with fifty observations draws near its mean; a
  sound never tried draws from Beta(1,1) and can come back anywhere — which is
  the exploration term, with no separate bonus bolted on. Uncertainty earns
  attention for free.
- An unseen pronunciation prompt's urgency is then `1 - min(ability)` over the
  card's phonemes.

Three things there were settled by measurement rather than by taste, and each
of the first two attempts *silently did nothing*:

| attempt | result |
| --- | --- |
| mean ability, clamped into a band around 0.85 | every card floors at the same value; feature inert |
| min ability, band around 0.85, top-N gate | perfect targeting, no variety: 3 decks of 20 shared 21 distinct cards |
| **min ability, full range, raced gate** | **32% of dealt cards carry a weak sound against a 10.6% base rate, 279 distinct cards over 15 decks** |

The mean is the better *predictor* — `summarise` scores an attempt as the share
of phonemes that came back clean — but it is the wrong thing to schedule on,
because every Spanish card is mostly vowels and /s/ and /n/ and one hopeless
/r/ moves the mean from 0.95 to 0.80. A card is worth saying because of its
hardest sound.

And the new-card gate had to become a race rather than a ranking, which is the
same lesson the deck itself learned in 008: a stable weakness produces a stable
ranking, and a stable ranking deals the same twenty cards until it is fixed.

**Pronunciation does not yet compete for slots in a mixed deck.** `study_deck`
deals one direction per card, so admitting `'pronounce'` to the default sides
would let a pronunciation prompt displace a translation prompt — a silent change
to a working scheduler on the strength of scores nothing has validated. It is a
fourth option on the direction picker instead. Revisit when `phone_state` has
enough in it to be trusted.

## Look and feel

Dark "brushed metal" theme. The vocabulary is small and lives in
`src/index.css` rather than in utility strings, because every surface needs
more than one background layer:

| Class                 | Use                                                     |
| --------------------- | ------------------------------------------------------- |
| `.plate`              | raised panel — specular gradient, lit top rim, drop      |
| `.plate-bright`       | more reflective variant, for cards and the brand mark    |
| `.well`               | recessed surface — inputs, meter tracks, list rows       |
| `.chrome` `.chrome-cyan` | gradient text, clipped to the glyphs                 |
| `.sheen` `.sheen-run` | specular band that sweeps across a surface               |
| `.ring-sweep`         | conic ring that orbits a border while something is loading |
| `.btn-*` `.input-metal` `.chip` `.keycap` `.label` | controls and small type |

Animation is part of the interaction, not decoration on top of it: the reveal
fires a sheen sweep, a ring pulse and a per-character entrance; a drag lights a
verdict-tinted bloom under the card and scales the stamp; a commit throws a
spark burst and flashes the edge of the screen; a pending translation scans the
target field and sweeps a ring around it. Keyframes live in
`tailwind.config.ts`; everything respects `prefers-reduced-motion`.

**The card gesture.** `FlashCard` keeps the drag out of React state: offset,
tilt and specular position are refs, written to the DOM in a single
`requestAnimationFrame` per frame (the faces read the highlight from inherited
custom properties). State drives only the flip, the reveal counter and the
leave animation. Two reasons, both learned the hard way:

- a state-driven offset re-rendered the whole card on every pointermove, with
  a forced layout read thrown in;
- and the release handler read the offset from its render closure, so the last
  `setDx` of a fast flick hadn't flushed — the card sprang back instead of
  answering, which is what made swiping feel unreliable.

A release now answers on distance **or** velocity (`releaseSpeed`), so a short
flick counts.

**The lean lives on its own layer** (`.card-tilt`), inside the drag layer and
`pointer-events: none`. It has to: a 3D lean on the element that *receives* the
pointer rotates its hit quad out from under the cursor, which drops the hover,
which resets the lean, which brings it back. Measured on a 7×5 grid over the
card, 17 of 35 points fell through to the untransformed ancestor — and since
Tailwind's preflight puts `cursor: pointer` on `[role="button"]` and the
ancestor was `cursor: auto`, the pointer flickered between hand and arrow
across half the card. With the lean on a pointer-transparent layer the same
grid loses 0 of 35. The card also sets its own `cursor: grab` / `grabbing`,
on both the drag layer and the card-sized wrapper around it, so no hit can
land on something with a different cursor.

Two traps worth knowing:

- `background-clip: text` (i.e. `.chrome`) does **not** reach descendants that
  have their own transform or filter — they paint in a separate layer and the
  glyphs come out transparent. Put `.chrome` on the animated element itself.
  `StaggerText` in `FlashCard` does this per character.
- Tailwind only emits opacity steps from its scale, so `bg-white/8` silently
  produces nothing. Use a real step or bracket notation (`text-white/[0.035]`).

## Translation suggestions

Typing in either side of the card form debounces for ~650ms, then asks the
`translate` edge function for the other side and offers it as a chip you tap to
accept. Failures are silent by design: a suggestion is a convenience and the
form stays usable without it.

The function requires a valid user JWT (`verify_jwt = true`), so it isn't an
open translation proxy.

**Swapping provider.** `supabase/functions/translate/provider.ts` defines a
`Provider` interface and exports `activeProvider`. MyMemory is free and
key-less but its quality on bare words is mixed — it sometimes returns a
phrase-match ("the house" → "con la casa"). To move to DeepL or an LLM, add a
provider in that file, point `activeProvider` at it, and add its key to `.env`;
nothing else changes.

## Deploying

Free-tier Supabase for the database, auth and the `translate` function; Vercel
for the built SPA; GitHub Actions ties them together on a push to `prod`.

```bash
git push origin main:prod
```

Migrations run before the web deploy, the full test suite (model-backed
integration tests included) gates both, and the workflow refuses to deploy if
public signup has been re-enabled on the production project — the deck is
shared, so any signed-in user can delete any card.

Setup, secrets, and the free-tier limits worth knowing are in
[docs/deploying.md](docs/deploying.md).

- Pronunciation is its own deck mode and does not yet compete for slots in a
